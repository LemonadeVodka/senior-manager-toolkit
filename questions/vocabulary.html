Pillar 4 · Lead With Questions

Credibility Habits & Vocabulary

Technical credibility for a leader comes from habits, not a computer science degree. Use the vocabulary correctly, follow up, translate clearly, and never pretend.

Credibility Habits

  • Learn the 30 terms below well enough to use them correctly in a sentence.
  • Read one design doc or postmortem a week, and note one question you'd ask.
  • Ask an engineer to teach you one concept a month. People love explaining their work.
  • Follow up on every question you asked (how).
  • Translate for executives: impact, risk, cost, and decision, never raw jargon.
  • Give credit by name when you present your team's technical work.

30 Core Terms

TermPlain meaningQuestion it should prompt
LatencyHow long something takes to respond"At the typical case, and at the slowest 5%?"
P50 / P95Typical response time / the slowest 5% of requests"Did the P95 change, or only the P50?"
Error rateShare of requests that fail"Failures users actually see?"
ThroughputHow much work the system handles per unit of time"How close are we to the limit?"
SLA / SLO / SLIA promise to customers / an internal target / the measurement itself"Are we inside our SLO this month?"
Error budgetHow much unreliability the SLO allows"How much budget is left?"
AvailabilityShare of time the service works"For whom, and measured how?"
ScalabilityAbility to handle more load"What breaks first at twice the traffic?"
CapacityHow much load we can handle before trouble"What's our headroom at peak?"
BottleneckThe slowest step that limits everything"Where's the bottleneck now?"
Blast radiusHow much is affected when something fails"How do we keep it small?"
RollbackUndoing a change"How fast, and has it been tested?"
Canary / staged rolloutReleasing to a small group first"What do we watch before expanding?"
Feature flagA switch that turns a feature on or off without a deploy"Can we turn it off quickly?"
Deploy / releasePutting code into production"How often, and how risky is each one?"
CI/CDAutomated testing and deployment pipeline"What's tested automatically before release?"
Technical debtShortcuts that make future work slower or riskier"What is it costing us now?"
RefactorRestructuring code without changing behavior"What does it make easier afterwards?"
APIHow systems talk to each other"Who depends on it, and what if it changes?"
DependencySomething we rely on that we don't control"What happens if it fails?"
Single point of failureOne component whose failure stops everything"Do we have any?"
Redundancy / failoverBackup components / switching to them"When did we last test failover?"
ObservabilityHow well we can see what the system is doing"Could we explain a problem from our dashboards?"
Monitoring / alertingWatching metrics / being notified when they're bad"Do alerts fire on user impact, or on noise?"
Incident / postmortemAn unplanned disruption / the blameless review after it"What did we change because of it?"
ToilManual, repetitive operational work"How much of the team's time is toil?"
On-callBeing responsible for responding out of hours"How many pages per week, and is it fair?"
Root cause / contributing factorsWhy something happened (usually several reasons)"What made this possible, not just who?"
MVPThe smallest version that delivers value"What's the smallest version we could ship first?"
Build vs buyMake it ourselves, or purchase it"Is this core to what makes us different?"
